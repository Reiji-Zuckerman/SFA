## 1. プロジェクトの背景と目的

### 1.1 事業構造

弊社は以下の3事業＋2つの横串組織で構成される。

| 区分 | 略称 | 内容 |
|------|------|------|
| 事業部 | SLS | ITコンサルティング事業 |
| 事業部 | PERM | 人材紹介事業 |
| 事業部 | ITSS | 人材派遣事業 |
| 横串組織 | IS | インサイドセールス（リード獲得・架電アプローチ） |
| 横串組織 | FS | フィールドセールス（初回商談・基本契約締結） |

### 1.2 プロジェクト目的

フロントライン（IS/FS）から各事業部へのシームレスな顧客パスを実現し、全社での売上最大化と業務効率化を両立する「統合型SFA」をゼロベースで構築する。

### 1.3 解決すべき現状の課題

| # | 課題 | 詳細 |
|---|------|------|
| 1 | 分断された顧客情報 | 事業部ごとに顧客アプローチが独立しており、クロスセル機会が個人の気付きや手動の会議（商談レコード確認会）に依存 |
| 2 | リードの使い捨て | 失注・保留顧客に対する「ネクストアクション（再アプローチ）」の管理機能がなく、機会損失が発生 |
| 3 | マーケティングROIの可視化不足 | どのチャネルで獲得したリードが最終的にどの事業部の売上に貢献したかを通期で追跡できない |

## 2. システム全体構想（アーキテクチャ方針）

### 2.1 システム間の役割分担

本SFAは既存の「パワーエイジレス」を置き換えるものではなく、役割を明確に切り分ける。

```
┌─────────────────────────────────┐     ┌─────────────────────────────────┐
│   新SFA（セールス・コックピット）  │     │  パワーエイジレス（デリバリー）    │
│                                 │     │                                 │
│  ・リード獲得〜基本契約締結       │ ──→ │  ・候補者の紐付け                │
│  ・事業部へのトスアップ           │ URL │  ・選考フェーズ管理              │
│  ・企業深耕・クロスセル管理       │ 連携 │  ・マッチング進捗管理            │
│  ・ネクストアクション管理         │     │                                 │
│  ・マーケティングROI追跡         │     │                                 │
└─────────────────────────────────┘     └─────────────────────────────────┘
        前工程（営業・顧客開拓）                後工程（デリバリー・マッチング）
```

### 2.2 パワーエイジレスとの連携方式

| 項目 | 方針 |
|------|------|
| 連携方式 | **【要検討】** URL遷移（Phase 1）→ API連携（Phase 2）の段階的アプローチを想定 |
| 企業データ同期 | **【要検討】** パワーエイジレス側の企業IDとSFA側のAccountを紐付ける方法 |
| データの正（マスタ）| **【要検討】** 企業マスタの正はどちらのシステムに持たせるか |

## 3. 業務ワークフロー

### 3.1 全体フロー

```
[リード獲得]  →  [ISアプローチ]  →  [FS商談]  →  [基本契約]  →  [事業部トスアップ]
    (IS)            (IS)            (FS)         (FS)          (自動通知)
                                                                    │
                                                    ┌───────────────┼───────────────┐
                                                    ▼               ▼               ▼
                                                [SLS案件]      [PERM求人]      [ITSS求人]
                                                (SFA管理)    (SFA→パワエジ)  (SFA→パワエジ)
                                                    │               │               │
                                                    ▼               ▼               ▼
                                               [受注/失注]     [受注/失注]     [受注/失注]
                                                    │               │               │
                                                    └───────────────┴───────────────┘
                                                                    │
                                                            [失注の場合]
                                                                    ▼
                                                        [再アプローチ予定日設定]
                                                                    │
                                                                    ▼
                                                        [ISダッシュボードに自動表示]
                                                                    ▼
                                                            [再架電ループ]
```

### 3.2 各ステップの詳細

#### STEP 1: リードジェネレーション（IS）

- 展示会・広告等で獲得したリードをSFAに登録
- 登録時に「流入チャネル」を必須入力とする
- 架電アプローチを実施し、アポ取得時にFSへパス

#### STEP 2: 初回商談・基本契約（FS）

- 初回商談を実施し、企業ニーズを整理
- 「基本契約」の締結をミッション → SFA上のステータス更新（全社取引可能フラグON）
- ヒアリング結果に基づき「SLS」「PERM」「ITSS」のニーズフラグをチェック

#### STEP 3: 事業部へのトスアップ＆クロスセル検知（自動化）

- FS（または他事業部営業）がSFA上で「他事業部ニーズ」フラグを立てる
- 対象事業部の責任者に自動通知 → 抜け漏れのないクロスセル

#### STEP 4: 事業部デリバリー・深耕

| 事業部 | SFA上での管理内容 | パワーエイジレス連携 |
|--------|-------------------|---------------------|
| SLS | 案件パイプライン（提案〜受注）、詳細ToDo | なし（SFA完結） |
| PERM | キーマン接触履歴、競合状況 | 求人・マッチング業務 |
| ITSS | キーマン接触履歴、競合状況 | 求人・マッチング業務 |

#### STEP 5: リードのリサイクル（全社共通）

- 失注・見送り時に「再アプローチ予定日」を設定
- 期日到来時にISダッシュボードに自動表示 → 再架電ループ

## 4. データ構造（オブジェクト設計）

全事業部が「1つの共通企業データ（Account）」を見ながら、それぞれの「商談・活動」をぶら下げる構造。

### 4.1 ER図（概念レベル）

```
┌──────────────┐       ┌──────────────┐
│   Account    │ 1   N │   Contact    │
│  （企業）     │───────│ （担当者）    │
└──────┬───────┘       └──────────────┘
       │ 1
       │
       │ N
┌──────┴───────┐
│  Opportunity │
│ （商談/案件） │
└──────┬───────┘
       │ 1
       │
       │ N
┌──────┴───────┐
│   Activity   │
```

### 4.4 ③ Opportunity（商談・案件データ）

ISのリード、FSの初回商談、各事業部の案件・求人を管理する「動的」なデータ。事業部ごとに表示項目を切り替え。

| フィールド名 | 型 | 必須 | 説明 |
|-------------|-----|------|------|
| opportunity_id | UUID | ○ | 一意の商談識別子 |
| account_id | FK(Account) | ○ | 紐付け企業 |
| record_type | ENUM | ○ | レコードタイプ（IS_LEAD / FS_DEAL / SLS_PROJECT / PERM_JOB / ITSS_JOB） |
| opportunity_name | VARCHAR | ○ | 商談名（例：「〇〇刷新プロジェクト」） |
| phase | ENUM | ○ | フェーズ（下記参照） |
| channel | ENUM | | 流入チャネル（展示会 / 広告 / 紹介 / HP問合せ / 自社開拓 / その他） |
| owner_id | FK(User) | ○ | 主担当者 |
| is_owner_id | FK(User) | | IS担当者 |
| fs_owner_id | FK(User) | | FS担当者 |
| bu_owner_id | FK(User) | | 事業部担当者 |
| expected_amount | BIGINT | | 想定金額（円） |
| expected_close_date | DATE | | 受注予定日 |
| reapproach_date | DATE | | 再アプローチ予定日（リサイクル用） |
| lost_reason | TEXT | | 失注理由 |
| power_ageless_url | VARCHAR | | パワーエイジレス連携URL |
| notes | TEXT | | 備考 |
| created_at | TIMESTAMP | ○ | 作成日時 |
| updated_at | TIMESTAMP | ○ | 更新日時 |

#### フェーズ定義（record_type別）

| record_type | フェーズ候補 |
|-------------|-------------|
| IS_LEAD | リード登録 → 架電中 → アポ取得 → FSパス済 |
| FS_DEAL | 初回商談 → ニーズ確認 → 基本契約交渉 → 契約締結 → 事業部トスアップ済 |
| SLS_PROJECT | 提案準備 → 提案済 → 交渉中 → 受注 → 失注 |
| PERM_JOB | ヒアリング → 求人獲得 → 紹介中 → 成約 → 失注 |
| ITSS_JOB | ヒアリング → 求人獲得 → 人選中 → 稼働開始 → 契約終了 |

## 5. ユーザーロール・権限設計

**【要検討】** 以下は想定案。実際の運用に合わせて調整が必要。

| ロール | 対象者 | 権限概要 |
|--------|--------|----------|
| ADMIN | システム管理者 | 全データのCRUD、マスタ管理、ユーザー管理 |
| MANAGER | 事業部長・マネージャー | 所属部門＋全社ダッシュボード閲覧、メンバーデータ編集 |
| MEMBER | IS/FS/事業部メンバー | 自担当データの編集、所属部門データの閲覧 |
| VIEWER | 経営層・他部門参照者 | 全社ダッシュボード閲覧のみ |

## 6. 通知・自動化要件

### 6.1 自動通知

| トリガー | 通知先 | 通知手段 | 内容 |
|----------|--------|----------|------|
| 他事業部ニーズフラグON | 対象事業部の責任者 | **【要検討】** Slack / メール / アプリ内 | 「○○社にて△△ニーズあり。対応をお願いします」 |
| 再アプローチ予定日到来 | IS担当者 | ダッシュボード表示 + 通知 | 「○○社の再アプローチ期日です」 |
| ISからFSへのパス | FS担当者 | 通知 | 「○○社のアポが取得されました」 |
| 商談フェーズ変更 | 関係者 | 通知 | 「○○案件のフェーズが△△に変更されました」 |
| ネクストアクション期限到来 | 担当者 | ダッシュボード表示 + 通知 | 「○○のタスク期限です」 |

### 6.2 自動化ルール

| ルール | 内容 |
|--------|------|
| 基本契約締結時 | Account の basic_contract_status を「締結済」に更新し、全社取引可能フラグを立てる |
| ISアポ取得時 | Opportunity の record_type を IS_LEAD → FS_DEAL に切り替え（またはFS_DEALを新規作成） |
| 失注時 | 再アプローチ予定日の入力を促すポップアップ表示 |

## 7. ダッシュボード・レポート要件

**【要検討】** 各ロール・部門ごとに必要なダッシュボードの洗い出しが必要。

### 7.1 想定ダッシュボード一覧

| ダッシュボード | 対象ユーザー | 主な表示内容 |
|---------------|-------------|-------------|
| ISダッシュボード | IS メンバー | 今日の架電リスト、再アプローチリスト、アポ獲得率推移 |
| FSダッシュボード | FS メンバー | 商談パイプライン、基本契約進捗、今週の商談予定 |
| 事業部ダッシュボード | SLS/PERM/ITSS | 案件パイプライン、売上予測、トスアップ未対応一覧 |
| 経営ダッシュボード | マネージャー・経営層 | 全社売上パイプライン、チャネル別ROI、事業部横断KPI |
| クロスセルレポート | 全社 | クロスセル機会一覧、他事業部ニーズフラグ立ち状況 |

### 7.2 マーケティングROI分析

流入チャネル別に以下を追跡可能とする。

- チャネル別リード数
- チャネル別アポ率・商談化率・受注率
- チャネル別最終売上貢献額（事業部横断）

## 10. 開発フェーズ（案）

**【要検討】** 段階的にリリースすることを推奨。

| Phase | スコープ | 目標 |
|-------|---------|------|
| Phase 1 | Account / Contact / Opportunity / Activity の基本CRUD、IS/FSワークフロー、基本ダッシュボード | 営業データの一元管理を実現 |
| Phase 2 | クロスセル自動通知、リサイクル自動化、権限管理の精緻化 | 自動化による抜け漏れ防止 |
| Phase 3 | マーケティングROIレポート、経営ダッシュボード、パワーエイジレスAPI連携 | データドリブンな意思決定基盤 |
