## 1. プロジェクトの背景と目的

### 1.1 事業構造

| 区分 | 略称 | 内容 |
|------|------|------|
| 事業部 | SLS | ITコンサルティング事業 |
| 事業部 | PERM | 人材紹介事業 |
| 事業部 | ITSS | 人材派遣事業 |
| 横串組織 | IS | インサイドセールス（リード獲得・架電アプローチ） |
| 横串組織 | FS | フィールドセールス（初回商談・基本契約締結） |

### 1.2 目的

フロントライン（IS/FS）から各事業部へのシームレスな顧客パスを実現し、全社での売上最大化と業務効率化を両立する「統合型SFA」をゼロベースで構築する。

### 1.3 解決すべき現状の課題

| # | 課題 | 詳細 |
|---|------|------|
| 1 | 分断された顧客情報 | 事業部ごとに顧客アプローチが独立しており、クロスセル機会が個人の気付きや手動の会議に依存 |
| 2 | リードの使い捨て | 失注・保留顧客に対する再アプローチ管理がなく、機会損失が発生 |
| 3 | マーケティングROIの可視化不足 | どのチャネルのリードがどの事業部の売上に貢献したか追跡できない |

### 1.4 利用規模

- 想定利用者数: 30名以上（IS + FS + SLS + PERM + ITSS + マネージャー + 経営層）

## 2. システム全体構想

### 2.1 SFAとパワーエイジレスの役割分担

```
┌──────────────────────────────────┐      ┌──────────────────────────────────┐
│    新SFA（セールス・コックピット）   │      │   パワーエイジレス（デリバリー）    │
│                                  │      │                                  │
│  【前工程: 営業・顧客開拓】        │      │  【後工程: マッチング】            │
│  ・リード獲得〜基本契約締結        │      │  ・候補者の紐付け                 │
│  ・事業部トスアップ               │      │  ・選考フェーズ管理               │
│  ・SLS案件のパイプライン管理       │      │  ・マッチング進捗管理             │
│  ・企業深耕・クロスセル管理        │ URL  │                                  │
│  ・ネクストアクション管理          │ 連携  │  ※ 企業マスタはパワーエイジレスが正 │
│  ・マーケティングROI追跡          │ ───→ │  ※ PERM/ITSS の求人・マッチングを  │
│                                  │      │    管理                           │
└──────────────────────────────────┘      └──────────────────────────────────┘
```

### 2.2 パワーエイジレス連携方針（決定済み）

| 項目 | 決定事項 |
|------|---------|
| 企業マスタの正 | **パワーエイジレスが正**。SFAはパワーエイジレスの企業IDを保持し参照する |
| 連携方式 | URL遷移によるワンクリック遷移（SFA → パワーエイジレス） |
| SLS案件 | SFA内で完結（パワーエイジレス連携なし） |
| PERM/ITSS案件 | SFAで営業活動を管理、求人・マッチング業務はパワーエイジレスで実施 |

### 3.2 ワークフロー詳細

#### STEP 1: リードジェネレーション（IS担当）

| 項目 | 内容 |
|------|------|
| トリガー | 展示会、広告、HP問合せ、紹介等でリード情報を取得 |
| 操作 | SFAにOpportunity（IS_LEAD）を新規登録 |
| 必須入力 | 企業名、流入チャネル、担当者情報 |
| 業務 | 架電アプローチを実施 |
| 完了条件 | アポ取得 → フェーズを「アポ取得」に更新し、FS担当者をアサイン |
| 自動処理 | FS担当者にSlack通知（「○○社のアポが取得されました」） |

**ポイント**: 同一のOpportunityレコードがIS → FS → 事業部と引き継がれる（新規レコードは作らない）。

#### STEP 2: 初回商談・基本契約（FS担当）

| 項目 | 内容 |
|------|------|
| トリガー | ISからのアポパス（Slack通知） |
| 操作 | Opportunityのフェーズを「初回商談」に更新 |
| 業務 | ① 初回商談でニーズヒアリング → ② 事業部ニーズフラグをON → ③ 基本契約交渉 |
| ニーズフラグ | SLS / PERM / ITSS それぞれのニーズ有無をAccount上で更新 |
| 自動処理 | ニーズフラグON時、対象事業部責任者にSlack通知 |
| 完了条件 | 基本契約締結（Account の契約ステータスを「締結済」に更新） |

**ポイント**: 基本契約が未締結でも事業部へのトスアップ（案件パス）は可能。契約ステータスとトスアップは独立して管理する。

#### STEP 3: 事業部トスアップ＆クロスセル検知

| 項目 | 内容 |
|------|------|
| トリガー | Account上の事業部ニーズフラグがONに変更された時点 |
| 自動処理 | 対象事業部の責任者にSlack通知（「○○社にて△△ニーズあり」） |
| 操作 | 事業部担当者が対応を開始 → Opportunityの record_type を事業部用に切替え、事業部担当者をアサイン |
| 意義 | 個人の気付きに依存せず、システム的にクロスセル機会を検知・通知 |

**【要検討: D-01】** 1つのAccountに複数事業部のニーズがある場合、Opportunityは事業部ごとに分けるか、1つのOpportunityに複数事業部を紐付けるか？

→ **推奨案**: 事業部ごとに別Opportunityを作成する。理由: フェーズ管理・金額管理が事業部ごとに独立するため。

#### STEP 4: 事業部デリバリー・深耕

**SLS（ITコンサル）**- SFA内で完結
| フェーズ | 主な活動 |
|---------|---------|
| 提案準備 | 顧客課題の深掘り、提案書作成 |
| 提案済 | 提案内容の説明、フィードバック回収 |
| 交渉中 | 金額・スコープ調整、契約条件交渉 |
| 受注 | 契約締結、プロジェクト開始 |
| 失注 | 失注理由記録 → リサイクルフロー |

**PERM（人材紹介）**- SFA + パワーエイジレス
| フェーズ | 主な活動 | 管理場所 |
|---------|---------|---------|
| ヒアリング | 求人要件の整理、キーマン情報収集 | SFA |
| 求人獲得 | 求人票確定、パワーエイジレスに求人登録 | SFA → パワエジ |
| 紹介中 | 候補者マッチング、面接調整 | パワエジ（SFAからURL遷移で確認） |
| 成約 | 内定・入社確定 | パワエジ → SFAの金額・フェーズ更新 |
| 失注 | 失注理由記録 → リサイクルフロー | SFA |

**ITSS（人材派遣）**- SFA + パワーエイジレス
| フェーズ | 主な活動 | 管理場所 |
|---------|---------|---------|
| ヒアリング | 派遣要件の整理、キーマン情報収集 | SFA |
| 求人獲得 | 求人確定、パワーエイジレスに登録 | SFA → パワエジ |
| 人選中 | 候補者選定、職場見学調整 | パワエジ（SFAからURL遷移で確認） |
| 稼働開始 | 派遣スタッフ就業開始 | パワエジ → SFAのフェーズ更新 |
| 契約終了 | 契約満了 or 更新判断 | SFA |

#### STEP 5: リードリサイクル（全社共通）

| 項目 | 内容 |
|------|------|
| トリガー | Opportunityが「失注」「見送り」に変更された時 |
| 操作 | 「再アプローチ予定日」と「失注理由」の入力を促す |
| 自動処理 | 再アプローチ予定日が到来 → ISダッシュボードの「再アプローチリスト」に自動表示 |
| 再アプローチ | ISが再度架電 → アポ取得でフローが再開 |

### 4.2 Account（企業マスタ）

全社共通の企業情報。パワーエイジレスの企業マスタが正であり、SFAはそのIDを保持して参照する。

| フィールド | 必須 | 説明 |
|-----------|------|------|
| 企業ID | ○ | SFA内の一意識別子 |
| パワーエイジレス企業ID | | パワーエイジレス側の企業IDとの紐付け |
| 企業名 | ○ | |
| 企業名カナ | | 検索・名寄せ用 |
| 業種 | | |
| 企業属性 | | SIer / 事業会社 / コンサルファーム / SES / メーカー 等 |
| Tier（優先度） | | S / A / B / C（**分類基準は後述**） |
| 基本契約ステータス | ○ | 未契約 / 交渉中 / 締結済 |
| 全社メインオーナー | | 現在最もその企業に入り込んでいる担当者 |
| SLSニーズフラグ | ○ | ON/OFF（Slack通知トリガー） |
| PERMニーズフラグ | ○ | ON/OFF（Slack通知トリガー） |
| ITSSニーズフラグ | ○ | ON/OFF（Slack通知トリガー） |
| 所在地 | | |
| 企業URL | | |
| 従業員数 | | |
| 年間売上高 | | |
| 備考 | | |

**【要検討: D-02】** Tier（優先度）の分類基準

現在「AIによる自動分類」とあるが、具体的にどの項目を基準とするか未定。候補:
- 売上規模 × IT投資意欲
- 過去の取引実績（受注金額・頻度）
- 事業部横断でのポテンシャル（複数ニーズの有無）

→ まずは手動設定で運用開始し、データが蓄積された段階で自動分類ルールを検討する方針を推奨。

### 4.4 Opportunity（商談・案件）

営業プロセスの「動的」なデータ。1つのレコードが IS → FS → 事業部 とフェーズ遷移する。1つのAccountに複数のOpportunityが存在しうる（事業部ごと、期間ごと）。

| フィールド | 必須 | 説明 |
|-----------|------|------|
| 商談ID | ○ | 一意識別子 |
| 紐付け企業 | ○ | Account への紐付け |
| 紐付け担当者 | | Contact への紐付け（主要コンタクト） |
| レコードタイプ | ○ | IS_LEAD / FS_DEAL / SLS_PROJECT / PERM_JOB / ITSS_JOB |
| 商談名 | ○ | 例:「○○刷新プロジェクト」「バックエンドエンジニア求人」 |
| フェーズ | ○ | レコードタイプに応じたフェーズ（下記参照） |
| 流入チャネル | ○（IS登録時） | 展示会 / 広告 / 紹介 / HP問合せ / 自社開拓 / その他 |
| IS担当者 | | リード獲得・架電担当 |
| FS担当者 | | 初回商談・契約担当 |
| 事業部担当者 | | デリバリー担当 |
| 想定金額 | | 円建て（売上予測用） |
| 受注予定日 | | |
| 再アプローチ予定日 | | 失注時のリサイクル用。期日到来でISダッシュボードに表示 |
| 失注理由 | | 失注時に記録（分析・改善用） |
| パワーエイジレスURL | | PERM/ITSS 案件でパワーエイジレスの該当画面に遷移するURL |
| 備考 | | |

#### フェーズ一覧

同一レコードがフェーズ遷移していく設計。レコードタイプの切替えがフェーズ遷移に伴って行われる。

```
【IS_LEAD フェーズ】
  リード登録 → 架電中 → アポ取得
        ↓（FS担当者アサイン → レコードタイプ切替）
【FS_DEAL フェーズ】
  初回商談 → ニーズ確認 → 基本契約交渉 → 契約締結 → 事業部トスアップ済
        ↓（事業部担当者アサイン → レコードタイプ切替）
【SLS_PROJECT フェーズ】          【PERM_JOB フェーズ】          【ITSS_JOB フェーズ】
  提案準備                         ヒアリング                     ヒアリング
  → 提案済                         → 求人獲得                     → 求人獲得
  → 交渉中                         → 紹介中                       → 人選中
  → 受注 / 失注                    → 成約 / 失注                  → 稼働開始 / 失注
                                                                  → 契約終了

【全タイプ共通】
  失注 → 再アプローチ予定日設定 → ISリサイクルへ
```

| 1 | 基本契約締結時 | Account の契約ステータスを「締結済」に更新 |
| 2 | フェーズが「アポ取得」に変更時 | レコードタイプをIS_LEAD → FS_DEALに切替え |
| 3 | フェーズが「失注」に変更時 | 再アプローチ予定日と失注理由の入力を促すダイアログ表示 |
| 4 | 事業部トスアップ時 | レコードタイプを FS_DEAL → SLS_PROJECT / PERM_JOB / ITSS_JOB に切替え |
