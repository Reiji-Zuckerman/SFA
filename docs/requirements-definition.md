## 1. プロジェクトの背景と目的

### 1.1 事業構造

| 区分 | 略称 | 内容 |
|------|------|------|
| 事業部 | SLS | ITコンサルティング事業 |
| 事業部 | PERM | 人材紹介事業 |
| 事業部 | ITSS | 人材派遣事業 |
| 横串組織 | IS | インサイドセールス（リード獲得・架電アプローチ） |
| 横串組織 | FS | フィールドセールス（初回商談・基本契約締結） |

### 1.2 目的

フロントライン（IS/FS）から各事業部へのシームレスな顧客パスを実現し、全社での売上最大化と業務効率化を両立する「統合型SFA」をゼロベースで構築する。

### 1.3 解決すべき現状の課題

| # | 課題 | 詳細 |
|---|------|------|
| 1 | 分断された顧客情報 | 事業部ごとに顧客アプローチが独立しており、クロスセル機会が個人の気付きや手動の会議に依存 |
| 2 | リードの使い捨て | 失注・保留顧客に対する再アプローチ管理がなく、機会損失が発生 |
| 3 | マーケティングROIの可視化不足 | どのチャネルのリードがどの事業部の売上に貢献したか追跡できない |

### 1.4 利用規模

- 想定利用者数: 30名以上（IS + FS + SLS + PERM + ITSS + マネージャー + 経営層）

## 2. システム全体構想

### 2.1 SFAとパワーエイジレスの役割分担

```
┌──────────────────────────────────┐      ┌──────────────────────────────────┐
│    新SFA（セールス・コックピット）   │      │   パワーエイジレス（デリバリー）    │
│                                  │      │                                  │
│  【前工程: 営業・顧客開拓】        │      │  【後工程: マッチング】            │
│  ・リード獲得〜基本契約締結        │      │  ・候補者の紐付け                 │
│  ・事業部トスアップ               │      │  ・選考フェーズ管理               │
│  ・SLS案件のパイプライン管理       │      │  ・マッチング進捗管理             │
│  ・企業深耕・クロスセル管理        │      │                                  │
│  ・ネクストアクション管理          │      │                                  │
│  ・マーケティングROI追跡          │      │                                  │
└──────────────────────────────────┘      └──────────────────────────────────┘
         ▲                                          ▲
         │              共有DB（企業マスタ）            │
         └────────────── 同一DBを参照 ────────────────┘
                       UIは完全に分離
```

### 2.2 パワーエイジレス連携方針（決定済み）

| 項目 | 決定事項 |
|------|---------|
| 企業マスタDB | **共有DB**。パワーエイジレスの企業マスタDBにSFA用カラム/テーブルを追加。UIは完全に分離 |
| 既存データ | パワーエイジレスの既存企業データが正 |
| 今後の運用 | SFA機能はパワーエイジレスに縛られない。SFA独自のデータ拡張が可能 |
| 連携方式 | URL遷移によるワンクリック遷移（SFA → パワーエイジレス） |
| SLS案件 | SFA内で完結（パワーエイジレス連携なし） |
| PERM/ITSS案件 | SFAで営業活動を管理、求人・マッチング業務はパワーエイジレスで実施 |

## 3. 業務ワークフロー

### 3.1 全体フロー

```
【IS/FS フェーズ】── 1つのOpportunityで管理 ─────────────────────────

[リード獲得] → [リード登録] → [架電中] → [アポ取得] → [初回商談]
  (展示会等)      (IS)          (IS)       (IS→FS)      (FS)
                                                          │
                                              [ニーズヒアリング]
                                              [ニーズフラグON]
                                              [基本契約交渉]
                                                          │
                                              [契約締結 or 契約前パス]
                                                          │
─────────────────────────────── トスアップ ──────────────────
                                                          │
              ここで事業部ごとに別Opportunityを新規作成（親子関係）
                                                          │
                 ┌────────────────────┼────────────────────┐
                 ▼                    ▼                    ▼

【SLS】                      【PERM】                  【ITSS】
クライアントPJ管理            クライアント事業部管理      クライアント事業部管理
(SFA完結)                    → 求人管理                + PJ管理 → 求人管理

┌──────────────┐         ┌──────────────┐        ┌───────────────────┐
│ SLS_PROJECT  │         │ ClientDept   │        │ ClientDept        │
│              │         │  └ PERM_JOB  │        │  └ ITSS_PROJECT   │
│ Task 1: 提案書│         │  └ PERM_JOB  │        │     └ ITSS_JOB    │
│ Task 2: 見積 │         │              │        │     └ ITSS_JOB    │
│ Task 3: 検証 │         │ (パワエジ連携)│        │                   │
│              │         │              │        │  (パワエジ連携)    │
│ → 受注/失注  │         │ → 成約/失注  │        │  → 稼働開始/失注   │
└──────────────┘         └──────────────┘        └───────────────────┘
       │                        │                        │
       └────────────────────────┼────────────────────────┘
                                │
                         【失注の場合】
                                ▼
                   [再アプローチ予定日 設定]
                                │
                                ▼
                   [期日到来 → ISダッシュボードに表示]
                                │
                                ▼
                         [再架電ループ]
```

### 3.2 ワークフロー詳細

#### STEP 1: リードジェネレーション（IS担当）

| 項目 | 内容 |
|------|------|
| トリガー | 展示会、広告、HP問合せ、紹介等でリード情報を取得 |
| 操作 | SFAにOpportunity（IS_LEAD）を新規登録 |
| 必須入力 | 企業名、流入チャネル、担当者情報 |
| 業務 | 架電アプローチを実施。結果をActivityに記録 |
| 完了条件 | アポ取得 → フェーズを「アポ取得」に更新し、FS担当者をアサイン |
| 自動処理 | FS担当者にSlack通知 |

#### STEP 2: 初回商談・基本契約（FS担当）

| 項目 | 内容 |
|------|------|
| トリガー | ISからのアポパス（Slack通知） |
| 操作 | 同一Opportunityのフェーズを「初回商談」に更新（レコードタイプ: FS_DEAL に切替） |
| 業務 | ① 初回商談でニーズヒアリング → ② 事業部ニーズフラグをON → ③ 基本契約交渉 |
| ニーズフラグ | SLS / PERM / ITSS それぞれのニーズ有無をAccount上で更新 |
| 自動処理 | ニーズフラグON時、対象事業部責任者にSlack通知 |
| 完了条件 | 基本契約締結 or 契約前パス |

**ポイント**: 基本契約が未締結でも事業部へのトスアップ可能。契約ステータスとトスアップは独立管理。

#### STEP 3: 事業部トスアップ（Opportunity分割）

| 項目 | 内容 |
|------|------|
| トリガー | ニーズフラグON + 事業部責任者が対応開始 |
| 操作 | **事業部ごとに新しいOpportunityを作成**（元のIS/FS Opportunityを親として紐付け） |
| SLSの場合 | SLS_PROJECT を作成。配下にTaskを登録していく |
| PERMの場合 | ClientDepartment を登録（未登録なら）→ PERM_JOB を作成し事業部に紐付け |
| ITSSの場合 | ClientDepartment を登録（未登録なら）→ ITSS_PROJECT を作成 → 配下に ITSS_JOB を作成 |
| 元のOpportunity | フェーズを「トスアップ済」に更新。以降は参照用（IS→FSの経緯を保持） |

**これにより D-06（フェーズ遷移履歴）を解決**: 元のIS/FS Opportunityが履歴として残り、事業部Opportunityは親IDで辿れる。

#### STEP 4: 事業部デリバリー

**SLS（ITコンサル）— SFA完結・プロジェクト管理型**

| フェーズ | 主な活動 | Task例 |
|---------|---------|--------|
| 提案準備 | 顧客課題の深掘り | 提案書作成、見積もり作成、技術検証 |
| 提案済 | 提案説明、フィードバック回収 | 提案書修正、追加資料作成 |
| 交渉中 | 金額・スコープ調整 | 契約書ドラフト、法務確認 |
| 受注 | 契約締結、プロジェクト開始 | キックオフ準備 |
| 失注 | 失注理由記録 → リサイクル | — |

**PERM（人材紹介）— クライアント事業部 → 求人管理**

| フェーズ | 主な活動 | 管理場所 |
|---------|---------|---------|
| ヒアリング | 求人要件の整理、事業部キーマン情報収集 | SFA（ClientDepartment + Activity） |
| 求人獲得 | 求人票確定、パワーエイジレスに求人登録 | SFA → パワエジ |
| 紹介中 | 候補者マッチング、面接調整 | パワエジ（SFAからURL遷移） |
| 成約 | 内定・入社確定 | パワエジ → SFAのフェーズ更新 |
| 失注 | 失注理由記録 → リサイクル | SFA |

**ITSS（人材派遣）— クライアント事業部 + PJ → 求人管理**

ITSSは「プロジェクト」の下に複数の「求人（ポジション）」がぶら下がる2階層構造。

| レベル | 例 | 説明 |
|--------|---|------|
| ClientDepartment | ○○社 開発部 | クライアント側の事業部 |
| ITSS_PROJECT | DX推進プロジェクト | プロジェクト単位の管理 |
| ITSS_JOB | SE求人 / PM求人 | 各ポジションの求人管理 |

| フェーズ（JOB単位） | 主な活動 | 管理場所 |
|---------|---------|---------|
| ヒアリング | 派遣要件の整理 | SFA |
| 求人獲得 | 求人確定、パワーエイジレスに登録 | SFA → パワエジ |
| 人選中 | 候補者選定、職場見学調整 | パワエジ（SFAからURL遷移） |
| 稼働開始 | 派遣スタッフ就業開始 | パワエジ → SFAのフェーズ更新 |
| 契約終了 | 契約満了 or 更新判断 | SFA |

#### STEP 5: リードリサイクル（全社共通）

| 項目 | 内容 |
|------|------|
| トリガー | 事業部Opportunityが「失注」「見送り」に変更 |
| 操作 | 「再アプローチ予定日」と「失注理由」の入力を促す |
| 自動処理 | 再アプローチ予定日到来 → ISダッシュボードの「再アプローチリスト」に自動表示 |
| 再アプローチ | ISが再度架電 → アポ取得でフローが再開 |

## 4. データ構造

```

**オブジェクト一覧（7種類）:**

| # | オブジェクト | 説明 | 用途 |
|---|-------------|------|------|
| 1 | Account | 企業マスタ | 全社共通の企業情報。パワエジと共有DB |
| 2 | Contact | 顧客担当者 | 企業に紐づくアプローチ先の人 |
| 3 | ClientDepartment | 顧客側事業部 | PERM/ITSSのクライアント事業部管理 |
| 4 | Opportunity | 商談/案件 | IS/FS商談、SLS案件、PERM求人、ITSSプロジェクト/求人 |
| 5 | Task | ToDo | Opportunityに紐づく個別タスク（主にSLS） |
| 6 | Activity | 活動ログ | 架電・MTG等の活動記録（純粋なログ） |
| 7 | User | システム利用者 | ログイン・権限管理 |

#### フェーズ一覧

```
【IS_LEAD】※ IS/FSで同一レコード
  リード登録 → 架電中 → アポ取得
      ↓（レコードタイプ切替: IS_LEAD → FS_DEAL）

【FS_DEAL】
  初回商談 → ニーズ確認 → 基本契約交渉 → 契約締結 → トスアップ済
      ↓（事業部ごとに子Opportunityを新規作成。元レコードは「トスアップ済」で保持）

【SLS_PROJECT】（親: FS_DEAL）
  提案準備 → 提案済 → 交渉中 → 受注 / 失注
  ※ 配下に複数の Task を持つ

【PERM_JOB】（親: FS_DEAL, 紐付け: ClientDepartment）
  ヒアリング → 求人獲得 → 紹介中 → 成約 / 失注

【ITSS_PROJECT】（親: FS_DEAL, 紐付け: ClientDepartment）
  企画中 → 進行中 → 完了
  ※ 配下に複数の ITSS_JOB を持つ

【ITSS_JOB】（親: ITSS_PROJECT）
  ヒアリング → 求人獲得 → 人選中 → 稼働開始 → 契約終了 / 失注
```

#### Opportunity 階層構造の具体例

```
例: ○○株式会社に SLS + ITSS のニーズがある場合

Opportunity: 「○○社 新規開拓」（FS_DEAL, フェーズ: トスアップ済）
  │
  ├── Opportunity: 「○○社 基幹刷新PJ」（SLS_PROJECT, フェーズ: 提案済）
  │     ├── Task: 提案書作成（完了）
  │     ├── Task: 見積もり作成（進行中, 期限: 3/10）
  │     └── Task: 技術検証（未着手, 期限: 3/15）
  │
  └── Opportunity: 「○○社 開発部 DX推進」（ITSS_PROJECT, フェーズ: 進行中）
        │   紐付け: ClientDepartment「開発部」
        │
        ├── Opportunity: 「SE求人（Java/3名）」（ITSS_JOB, フェーズ: 人選中）
        │     パワーエイジレスURL: https://...
        │
        └── Opportunity: 「PM求人（1名）」（ITSS_JOB, フェーズ: ヒアリング）

### 4.6 Task（ToDo）

| # | トリガー | 通知先 | メッセージ例 |

| 2 | Opportunity のフェーズが「アポ取得」に変更 | アサインされたFS担当者 | 「○○社のアポが取得されました」 |
| 3 | Opportunity のフェーズ変更 | 関係者（IS/FS/事業部担当） | 「○○案件のフェーズが △△ に変更されました」 |
| 4 | 再アプローチ予定日が当日に到達 | IS担当者 | 「○○社の再アプローチ期日です」 |
| 5 | Task の期限が当日に到達 | Task担当者 | 「○○のタスク期限です」 |
| 6 | トスアップ後N日間、事業部が未対応 | 事業部責任者（リマインド） | 「○○社のトスアップが未対応です（N日経過）」 |

### 7.2 自動化ルール

| # | トリガー | 処理内容 |
|---|----------|---------|
| 1 | 基本契約締結時 | Account の契約ステータスを「締結済」に更新 |
| 2 | フェーズが「アポ取得」に変更時 | レコードタイプを IS_LEAD → FS_DEAL に切替え |
| 3 | 事業部トスアップ時 | 事業部別の子Opportunityを新規作成（親子関係で紐付け）。元のFS_DEALは「トスアップ済」に |
| 4 | フェーズが「失注」に変更時 | 再アプローチ予定日と失注理由の入力を促すダイアログ表示 |

## 8. 決定事項・未決事項

### 8.1 決定事項

| # | カテゴリ | 決定内容 |
|---|---------|---------|
| 1 | リードパス | IS → FS は同一Opportunityのフェーズ遷移 |
| 2 | トスアップ | FS → 事業部は事業部ごとに別Opportunityを新規作成（親子関係） |
| 3 | 企業マスタ | パワエジと共有DB。既存データはパワエジが正。今後SFAは独立拡張可能。UIは完全分離 |
| 4 | 基本契約 | 未締結でもトスアップ可能（柔軟運用） |
| 5 | 通知 | Slack |
| 6 | SLS | SFA完結（パワエジ連携なし）。プロジェクト管理型でTask（複数ToDo）を管理 |
| 7 | PERM | クライアント事業部管理 → 求人管理。パワエジ連携あり |
| 8 | ITSS | クライアント事業部管理 + プロジェクト管理 → 複数求人管理。パワエジ連携あり |
| 9 | UI | SFA型（リスト+詳細画面） |
| 10 | フェーズ履歴 | 元のIS/FS Opportunityを「トスアップ済」で保持。事業部Opportunityは親IDで辿れる |
| 11 | モバイル | 劣後 |

### 8.2 未決事項

| # | カテゴリ | 論点 | 現状の想定 |
|---|---------|------|-----------|
